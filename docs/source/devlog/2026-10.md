# Development log - 2026-10

## 2026-10-01 - Host scripts resolve Python 3.11+ instead of trusting python3

### Result

- scripts/setup.sh and scripts/sync-runtime-surfaces.sh route every inline
  Python program through one resolver, scripts/lib/runtime-python.sh:
  AGENT_RUNTIME_PYTHON, then python3.14 down to python3.11, then Homebrew
  python3 at its standard prefixes, then python3 only when it is 3.11+.
- Without a suitable interpreter both scripts stop before planning or applying
  any mutation and name what to install. setup.sh defers that failure only when
  its own CLI-tools step will install Homebrew python@3, which every profile
  now lists for macOS hosts.

### Why / context

- The agent-hook policy sync imports tomllib (Python 3.11+). macOS login shells
  commonly resolve python3 to the system 3.9 interpreter ahead of Homebrew, so
  setup rendered and installed both products and then failed in the agent-hook
  step, leaving the host half-synced. Linux hosts and CI ship a modern python3,
  so the gap never surfaced there.
- Shell PATH order stays untouched: the scripts find the interpreter
  themselves. Linux hosts skip the python formula because their system python3
  is already new enough.

### Evidence

- tests/ci/test_runtime_python_resolver.py stages a PATH whose only python3 is
  a 3.9 stub. Before the fix all seven cases failed (sync died with the stub
  tomllib error; setup planned commands first); after it they pass on Linux and
  under macOS bash 3.2, where the resolver picked Homebrew python3.14 with the
  default login PATH.

## 2026-10-01 - The default-delivery guard classifies read-only inventories as reads

### Result

- Read-only cross-repository inventories no longer fail closed as unverified
  delivery: `[`/`[[` tests skip operand scanning, `${m%|*}` and `$(( ... ))`
  stay one word, only assignment-position words assign PATH, the Git builtin
  list is probed outside an unresolvable `git -C` target (and the baseline now
  includes `merge-base`), `~/.../tool` is a stable basename like
  `$HOME/.../tool`, and an unquoted here-doc body fed to cat, python, or
  jq keeps only its command substitutions.
- semantic-commit help, dry-run, and validate-only now count only after every
  earlier word is a literal, known option or value, as the DSH port does since
  sympoies/nils-cli#2016 and #2020; a dynamic word, an unknown option, or a
  redirection-like word in a value slot is classified as authoring.
- Unverified refusals name the word they could not classify (`word=`), the
  command that tainted executable resolution, and a missing
  `refs/remotes/origin/HEAD` with its `git remote set-head origin --auto`
  repair.

### Why / context

- The ops coordinator rewrote gh api, git show/log, merge-base, and
  agent-session message loops several times per task because parser artifacts
  read as opaque executables; the message spoke only about delivery, so a
  misclassified read was indistinguishable from a real refusal.
- Replaying the coordinator's blocked commands showed that the Python guard
  still admitted the semantic-commit flag-swallowing shapes that nils-cli fixed
  only in its Rust DSH port, so `semantic-commit commit $OUT --dry-run` on a
  default-branch checkout passed. The fix had to land here as well, not only in
  the port.
- Unquoted here-doc bodies stay visible for any command outside the
  data-consumer allowlist, and for a consumer whose output feeds a pipe or
  process substitution, so `cat <<EOF | bash` is still classified; reducing
  them for every non-shell command would have widened the existing quoted-body
  gap.

### Evidence

- Before the change, the new regression tests failed in 37 subtests (the read
  shapes, the semantic-commit bypass shapes, the opaque-word messages, and the
  literal-test candidate scan); they pass after, together with the existing
  default-delivery and hook suites. The one changed existing assertion is that
  `cat <<EOF` prose now passes while a substitution in it, an unknown consumer,
  and `| bash` stay blocked.
- The pre-merge specialist and red-team wave found adjacent bypasses in the
  relaxations: a here-doc delimiter split by a line continuation, here-doc
  bodies reaching a shell through `<(`, a grouped pipe, or a written script
  file, PATH
  assignments after reserved words, the `$${` PID expansion read as `${`, and
  `-C`-relative `git send-pack`, plus a zsh `word(N)` qualifier swallowing
  `--dry-run`. Each is now a refused regression case, and raw `send-pack` and
  `http-push` fail closed outright.

## 2026-10-01 - Claude loads AGENTS.md only through a sync-managed user setting

### Result

- scripts/sync-runtime-surfaces.sh now merges
  pluginConfigs["agents-md@builtin"].options.instructionFiles =
  "claude-md-and-agents-md" into the Claude user settings.json alongside the
  hook merge, refuses a non-object pluginConfigs chain instead of overwriting
  it, and fails apply verification when the value is missing. AGENTS.md,
  DEVELOPMENT.md, README.md, the harness-shape docs, and the Claude
  project-prompt surface row no longer claim Claude reads AGENTS.md natively;
  they name this setting.

### Why / context

- The earlier entry today assumed native loading. The builtin agents-md plugin
  loads AGENTS.md only when no CLAUDE.md, .claude/CLAUDE.md, or CLAUDE.local.md
  exists in the working directory or an ancestor, exempting only the active
  config directory file. Sessions here run with a per-account CLAUDE_CONFIG_DIR
  whose CLAUDE.md and settings.json symlink into ~/.claude, so
  ~/.claude/CLAUDE.md becomes an ordinary ancestor for every repository under
  the home directory and silently suppressed AGENTS.md once the repo-root
  import wrappers were removed. The key is honored only in user, --settings, or
  managed settings, so the kit-owned user settings merge is its owner; a
  hand-applied jq edit could be dropped by any regenerating writer.

### Evidence

- The new meta.sync-runtime-surfaces.claude-agents-md probe failed before the
  change (verify_claude_agents_md_setting undefined, key not merged) and passes
  after: it preserves sibling pluginConfigs and options keys, is idempotent
  across two applies, leaves dry-run and invalid-shape files untouched, and
  fails verification on a settings file without the key. The support-matrix
  golden was refreshed from manifests/surfaces.yaml.

### Links

- <https://code.claude.com/docs/en/memory.md#when-claude-code-reads-agents-md>

## 2026-10-01 - Repositories no longer keep a repo-root CLAUDE.md

### Result

- Project policy lives only in `AGENTS.md`, which Claude Code reads natively
  since 2.1.277. The Claude project-prompt surface now names `AGENTS.md` with
  that floor, the rendered home prompt says a closer `AGENTS.md` overrides it
  for every product, and the project-skill templates stop inspecting or
  searching a repo-root `CLAUDE.md`. This repository deleted its own
  `@AGENTS.md` import wrapper and the `.gitignore` negation that kept it
  tracked.
- The home install `~/.claude/CLAUDE.md` is a different file and is unchanged:
  setup, sync, and the container image still link it to the rendered
  `AGENT_HOME.md`.

### Why / context

- Claude Code prefers a repo-root `CLAUDE.md` over `AGENTS.md` when both exist,
  so a wrapper is at best redundant and at worst a second copy that drifts.
  Nothing generated the wrapper; it existed only because policy text told
  agents to create or keep it.
- Claude still does not discover skills from `.agents/skills/`, and settings,
  hooks, and agents stay under `.claude/`, so the `.claude/skills` bridges are
  kept.

### Evidence

- The meta home-prompt smoke now asserts the neutral and Claude renders say
  "`AGENTS.md` may extend or override it."; both assertions failed against the
  old template and pass after. The surfaces manifest validates with the new
  `#2-project-scope-prompt-agentsmd` anchor, and the render goldens and root
  support matrix were refreshed from source.

### Links

- <https://code.claude.com/docs/en/memory>

## 2026-10-01 - Program trackers are maintained through forge-cli issue tracker

### Result

- nils-cli v1.31.2 is the validated release; v1.31.1 stays the compatibility
  minimum. The validated Linux archive digests, Docker defaults, README,
  surface snapshot, and harness mirrors moved together.
- Program trackers now lint a filled tracker with `forge-cli issue tracker
  lint`, tick a closed child with `tick --pr --comment-file`, regenerate the
  dependency graph with `graph --write` after any row change other than a tick,
  and require `lint --check-state` before closeout, instead of hand-editing a
  checkbox or the Mermaid block. The Tracker Commands section of
  `issue-follow-up`'s `references/program-mode.md` is the one source for these
  commands and their manual equivalents; `deliver-dispatch-plan`, its issue
  record contract, and `work-modes.md` point to it.

### Why / context

- Program `work-mode-board-2026-09`: item S1 made the phase table
  machine-readable, and item S2 shipped the three commands in nils-cli
  v1.31.2, which parse rows by `references/tracker-row-grammar.md`. This item
  adopts them.
- No `required_clis[]` floor moved. A lock-step floor cannot exceed the release
  minimum, and nothing at v1.31.1 became unusable: the skills keep the
  grammar-defined manual path for a `forge-cli` without `issue tracker`, as the
  devlog capability does for a host without `devlog`. Requiring the commands
  everywhere would be an explicit compatibility retirement that moves minimum.
- The rest of `v1.31.1...v1.31.2` needed no migration: the `agent-session`
  mailbox notification wording already matches `session-coordination.md`,
  `agent-hook` now keeps Claude Stop warnings model-invisible, and the other
  `agent-session` and `claude-cli` fixes change no consumed command, flag, or
  envelope.

### Evidence

- The validated digests come from the release's published `.sha256` assets,
  which equal the GitHub asset digests: linux_amd64
  `7af4e8e17ca3bc78bbc7766f93e308c4a0608680bf8516e33747ccf76c07df86`,
  linux_arm64
  `d76784470b4216d61df335e0a442fd9601629ba4aabe6432a68ba5b5ee72eefe`.
- The version-policy test failed on the unmoved validated role before the pin
  change and the dispatch rendered-route smoke failed on the old tick wording
  before the skill change; both pass after.
- The dispatch and issue program-mode smokes exercise `tick`, `graph
  --body-file --write`, and `lint --check-state` on the local provider under
  v1.31.2 and read the ticked row and checkpoint back. They take the manual
  path only under exact v1.31.1, where `forge-cli issue tracker --help` exits
  64. A forge-cli newer than the minimum must pass the probe: with it shadowed
  to fail under v1.31.2, both cases fail, and each case note names the path it
  ran.
