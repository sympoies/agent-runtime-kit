# Development log - 2026-09

## 2026-09-05 - adopted nils-cli v1.28.0, and two invariants that said no first

**Result**

- `validated_tag` moves to `v1.28.0` with its published release digests, mirrored
  across the surface snapshot, README, all three harness-shape docs, the
  Dockerfile packaging pins, and the version-policy test.
- `minimum_supported_tag`, its retained lane digests, and every
  `required_clis[]` floor are unchanged. This uptake retires no compatibility.
- The posting contract and the four skill bodies that describe the
  `provider-review` bundle now state the v1.28.0 behavior instead of the
  permissive behavior it replaced.

**Why / context**

`v1.28.0` carries sympoies/nils-cli#1613: the publication-bound
`provider-review` and `pr-comment` profiles refuse to invent report metadata,
and `forge-cli pr review validate --specialist-report` rejects the retired
placeholder sentinels. Before it, a missing flag produced
`Reviewable: not provided` in a body published under the reviewer's name.

**Two invariants rejected the first attempt, and both were right**

- Raising the `review-specialists` per-binary floor to `1.28.0` failed
  `tests/ci/test_nils_cli_version_policy.py` with *a lock-step required CLI
  floor cannot exceed the release minimum*. Those floors guard against a
  **partial** release inside the admitted range; using one to demand a newer
  surface would raise the effective minimum without the compatibility-retirement
  evidence that decision requires. The floor stayed at `1.27.27`.
- Rewriting the surface snapshot then tripped the historical-entry guard in
  `tests/runtime-smoke/cases/code-review/run.sh`, which fails when a historical
  bullet claims to be a *current* compatibility minimum. The rewrite had pushed
  the current-roles sentence down into that range. The roles are now stated once,
  above it.

The honest consequence of the first: a host between `v1.27.35` and `v1.28.0` is
still admitted and still renders the old permissive body. The skills bind the
metadata flags regardless of host version, so the documented path is safe either
way — the released guard is defense in depth, not the primary control.

**Follow-ups**

- Only four of the five metadata flags are enforced; `--lens-verdict` keeps a
  findings-derived fallback. The contract asks callers to bind it anyway,
  because the fallback cannot express `blocked` or `follow-up-pass`.

## 2026-09-05 - a published review header said "not provided", and the Claude reviewers had no model

**Result**

- Every skill surface that showed the `review-specialists bundle --profile
  provider-review` command omitted `--reviewable`, `--lens`, `--lens-verdict`,
  `--scope`, and `--evidence-reviewed`. Only the reference contract listed
  them. An agent that copied the skill published a review whose header read
  `Reviewable: not provided`, `Lens: unspecified`, `Scope: not provided`.
- The four call sites now carry or name the required flags, and both the skill
  and the posting contract state that `--evidence-reviewed` is published
  verbatim and must never be an absolute local path.
- The eight Claude reviewer subagents now pin `model: opus` and
  `effort: medium`. They previously carried no model frontmatter at all and
  silently inherited whichever model the parent session happened to run, while
  their Codex counterparts had pinned `model` and `model_reasoning_effort`
  since they were written.
- `code-review.outcome-routing.provider-review-metadata` is a new
  runtime-smoke probe. It fails when a `--profile provider-review` call site
  loses a metadata flag or the portable-evidence rule.

**Why / context**

- The renderer treats all five as optional and substitutes `not provided` /
  `unspecified`. That is a reasonable default for a local report and the wrong
  one for a published body, and nothing between the renderer and the provider
  disagreed: `forge-cli pr review validate --specialist-report` accepted a body
  carrying both the placeholders and a `$HOME`-prefixed evidence path.
- So the only place the requirement lived was prose in one reference document,
  and the copyable command three files away contradicted it. The skill example
  is what gets used; a contract the example does not satisfy is not enforced by
  anything.
- The missing reviewer model pin is the same shape of gap in a different
  surface. Both products render from the same source tree, and only one branch
  of the template had ever been given a model, so the divergence never showed
  up as a diff — it showed up as Claude reviews whose depth depended on the
  parent session.

**Evidence**

- Red first: the new probe failed on the unmodified tree
  (`total=13 pass=11 fail=2`, the second failure being an unrendered `build/`
  tree), then passed after the repair (`total=13 pass=13 fail=0`).
- `scripts/ci/all.sh` full stack.
- Golden refresh across claude, codex, hermes, home-prompt, and support-matrix;
  only the claude agent goldens moved.

**What review caught, and why it mattered**

The first repair was wrong in a way worth recording. The new probe grepped
whole files — and the same commit added, to the files it guards, a sentence
naming all five flags. Every assertion was satisfied by that prose, so the
canonical command block could have lost all five flags with the probe still
green. The red-team lens found it; a mutation test confirmed it (strip
`--reviewable` from the posting contract's bash block only, leaving the prose,
and the probe passed). The probe now extracts the fenced block containing
`--profile provider-review` and asserts against that alone.

Two lenses independently found the deeper gap: the Claude reviewer pins had no
fail-closed owner. The Codex branch is guarded by `codex_reviewer_profile_errors`;
the Claude branch was guarded only by rendered goldens — and `ci/all.sh`
position 6 *regenerates* goldens before diffing, so a template that drops its
pin produces a matching golden and passes. That is the same detection gap that
let the missing model exist in the first place, and the repair would have
shipped without closing it. The audit now asserts both Claude keys, with
negative fixture cases for a removed pin and a drifted one.

The api-contract lens also settled the open question about `effort` by probing
the shipped binary rather than reasoning about it: the agent-definition schema
documents both keys, `effort: "bogus"` is rejected with an explicit validation
error, and `medium` and `opus` are accepted.

**Follow-ups**

- The renderer and `pr review validate --specialist-report` both accept a
  placeholder header and a local path in a body destined for publication.
  Documentation now closes the path an agent actually walks, but the
  deterministic surfaces should reject it too. Routed to sympoies/nils-cli.
- Codex pins `reviewer-quick` at `low` effort while Claude now pins every lens
  at `medium`. Deliberate for now — the two products' effort scales are not
  comparable — but worth revisiting if quick-pass cost matters.
- `effort` was verified on Claude Code 2.1.261, later than the `min_product`
  recorded for the subagent-definitions surface. A host below that build should
  be re-checked before relying on the pin.

## 2026-09-03 - the artifact-routing hook broke every Claude Bash call, and why nothing caught it

**Result**

- Deploying the previous day's artifact-routing rule made every Claude `Bash`
  tool call fail with `dispatch-child-budget-exceeded`. The session was
  unusable until the Claude hook ingress was removed by hand.
- The repair moved the check out of its own rule and into
  `portable-paths-scan`, a handler already registered on all five affected
  dispatch groups. `block-agent-artifact-routing` is deleted; enforcement
  behavior is unchanged.
- `tests/ci/test_hook_dispatch_budget.py` is new and runs at position 13 of
  `scripts/ci/all.sh`. It fails the build when a dispatch group can no longer
  fan out, which is the check whose absence let this ship.

**Why / context**

- `agent-hook` caps executable capabilities per `(product, event, matcher)`
  dispatch group at `MAX_EXECUTABLE_CAPABILITIES = 17`
  (`crates/agent-hook/src/evaluator.rs:29`). Claude's `Bash` group was already
  at exactly 17. Adding one rule made it 18.
- The cap is evaluated statically in `prepare()`
  (`crates/agent-hook/src/evaluator.rs:264`), before any handler runs. So the
  failure was total and deterministic from the first call after deploy, not an
  intermittent load-dependent one. That is the good news in an otherwise bad
  outcome: it could not have silently degraded.
- The cap has no configuration knob, and `providers.mode = "shadow"` does not
  relieve it: a rule with `override_class = "locked"` forces
  `ProviderMode::Enforce` regardless of provider config
  (`crates/agent-hook/src/contract.rs:627`). The documented-looking escape
  hatch is not one.
- 17 is a latency budget, not an arbitrary number. Each executable capability
  is a child process spawned on every matching tool call, with a 5 s timeout
  each and a *shared* 512 KiB output ceiling
  (`evaluator.rs:28-30`). Raising it makes every tool call in that group pay
  for the added fan-out, and shrinks each child's share of the output budget.
  That is why the fix was consolidation, not a request to raise the cap.

**Why nothing caught it**

- The change was valid at every layer that was checked. The policy bundle
  parsed, the manifests were consistent, 435 hook tests were green, and the
  `sync-runtime-surfaces` dry run was clean. No gate asked the one question
  that mattered: does the resulting fan-out still fit.
- Measured headroom after consolidation: Claude `Bash` **0**, Codex `Bash` 1.
  The group that broke is still at the cap. Nothing about this repair created
  slack, which is precisely why the gate is the durable part of it.
- The new gate deliberately does not reimplement the capability
  classification. Which capabilities count as executable is the binary's
  business and has changed across releases; a local copy would drift and give
  false comfort. It dispatches a probe through the installed `agent-hook` and
  asserts the budget error does not come back.

**Evidence**

- Two rounds of pre-merge review found two real defects in the repair itself,
  both worth recording because each was a fix that would have looked fine:
  - **The gate shipped with the failure it exists to prevent.** `dispatch()`
    failed only on unparseable JSON, so any *other* error - a digest mismatch,
    `provider-target-untrusted`, a future flag change - returned valid JSON
    with a non-budget code and counted as a pass. A reviewer reproduced a false
    PASS across all eight probes with the budget never evaluated. Any non-`ok`,
    non-budget outcome now fails and names the probes;
    `test_gate_fails_when_the_probe_cannot_reach_budget_evaluation` pins it.
  - **An inverted assertion justified by a false claim.** A MultiEdit test was
    flipped from `assertNotIn` to `assertIn` on the stated ground that the
    portable-paths half is a no-op there because `proposed_content` returns
    `""`. That is only one of two content sources: `patch_text_candidates`
    recurses into `edits[]`, so embedded apply-patch text does raise a hit.
    The inversion was correct on the merits; the reason given for it was not.
- Consolidation verified as a line-for-line port: same candidate sources, same
  lexical/physical dual judgment, same `.cache` short-circuit, same marker
  carve-out, same container exemption, same rule posture. Coverage is 1:1 -
  every group that carried the deleted handler now carries
  `portable-paths-scan`.
- The escape hatch is scoped by execution, not by inspection:
  `SKIP_PORTABLE_PATH_SCAN=1` still blocks `agent-out` writes and repo-local
  `.cache` scratch while waiving portable-path hits.
- Baselines independently re-derived from the policy bundle: 102 rules, 68
  registrations, 21 handlers.
- `tests/hooks/run.sh` 437 passed; `tests/agent-hook/run.sh` green;
  `scripts/ci/all.sh` positions 1-17 OK.
- Deployment was verified behaviorally rather than from the sync summary: 18
  cases driven through the deployed handler in each of the two live product
  homes, 36 checks, covering both what must block and what must keep working
  (`.cache/agent-validation/`, the `.cache` container itself, the XDG cache,
  `node_modules/.cache`, read-only `ls`, and `agent-out project` itself).

## 2026-09-02 - agent artifact routing became enforced, not just documented

**Result**

- New shared hook `block-agent-artifact-routing` denies writes to any
  `agent-out` path segment and to repo-local `.cache/` scratch outside the
  sanctioned `.cache/agent-validation/` marker subtree. Registered for Codex and
  Claude across Bash, Write/Edit/NotebookEdit, apply_patch, and MultiEdit.
- `AGENT_HOME.md` now says "Allocate temporary/debug/runtime evidence with
  `agent-out project`" instead of "Route ... to `agent-out`".
- Both nils-cli version roles moved to v1.27.35, retiring the v1.27.27 floor.

**Why / context**

- `agent-out` is a command that allocates a run directory outside the checkout.
  The always-on home prompt named it in a position where it reads as a
  directory, and agents acted on that reading. Artifacts had spread across four
  roots -- 566 entries under the state home's `agent-out/`, 105 under the home
  root's, 56 under the XDG state root's, and six repo-local `agent-out/` trees
  -- against 236 on the canonical allocated route.
- The unambiguous wording already existed in `files-hooks-validation.md`, but
  that file only loads when the `project-dev` intent is active, so ordinary
  tasks never saw it. Nothing enforced the rule at runtime.
- `128de6a6` (#83) addressed this class with wording alone; the most recent leak
  postdates it. That is why this change ships a runtime block and not only a
  better sentence.
- The block message names the allocation command *and* closes off the adjacent
  wrong answer (hand-building the path). A message that states only the rule is
  what left the previous fix ineffective.
- `.cache/agent-validation/` is legitimate and stays allowed: `AGENT_DOCS.toml`
  declares it and the finish-line gate reads it. Its presence in every repo is
  precisely what invited the `.cache/` scratch spillover, so the rule is scoped
  to the repository root rather than matching a bare `.cache` segment -- the XDG
  cache is not a checkout.

**Evidence**

- `runtime-kit.handler.v1` resolves handler IDs through an allowlist compiled
  into the nils-cli binary, so the handler could not dispatch until the ID
  shipped upstream. `tests/agent-hook/run.sh` failed 23 assertions with
  `handler-id-unsupported` before v1.27.35.
- Below-minimum proof for the floor retirement: `tests/agent-hook/run.sh` under
  `release:v1.27.27` still fails `handler-id-unsupported`, so the policy bundle
  does not load at all there and the old floor would have been a false claim.
- `tests/hooks/run.sh` 433 passed; `ci/all.sh` positions 1-17 OK.
- `audit-drift` caught a retired `$AGENT_HOME` literal in the first draft of the
  block message (`agent-home-leak`). Removing it improved the message: it now
  points at the path the command prints rather than a path template, which is
  the same lesson the hook exists to teach. A regression asserts the anchor
  cannot return through a block message.
- The home prompt sits under a hard 4096-byte budget with 18 bytes of codex
  headroom, so the wording fix was byte-constrained; codex now renders 4093.

## 2026-09-01 - agent-hook latency gate made robust to runner noise

**Result**

- The `agent-hook` shadow-dispatch latency gate now re-measures up to three
  batches and grades the best one, instead of failing on a single batch whose
  p95 was lifted by host scheduling stalls.
- The 25 ms budget, the 35-sample batch size, the p95 statistic, and the
  CI-hard / host-advisory enforcement split are all unchanged.

**Why / context**

- The `main` CI run for the devlog commit failed the gate with `p50 3.805 ms`
  and `p95 67.662 ms` against a 25 ms budget: two stalled samples out of 35,
  with the median at roughly a seventh of the budget. That commit touched only
  documentation, the devlog helper, and its test, so the dispatch path was not
  involved.
- Relaxing the budget would have traded away real regression detection for
  noise tolerance. A genuine dispatch regression shifts the whole distribution
  and therefore misses the budget in every batch, while a scheduling stall does
  not survive re-measurement, so re-measuring separates the two without moving
  the threshold.
- The emitted report gained `attempts` and `max_attempts` so a run that needed
  a retry stays visible rather than looking clean.

**Evidence**

- A regression probe with the budget forced to 0.001 ms still fails, after
  exhausting all three attempts: `attempts=3`, `exceeded=true`. This confirms
  the retry cannot mask a persistent regression and terminates.
- The unmodified gate passes on the first attempt on a quiet host:
  `attempts=1`, `p50 5.54 ms`, `p95 6.175 ms`, budget 25 ms, enforcement hard.
- `tests/agent-hook/run.sh` and the full `scripts/ci/all.sh` stack pass.
